# Absolute, translatable, human-useful delivery indicators for a polyrepo harness — final recommendation

**Headline finding.** Not one of the 22 candidates survived the adversarial pass in its stated form. The recurring reasons are structural, not cosmetic: (a) a "task" is a human planning cut, so every per-item count/rate is relative to granularity; (b) pooled cross-repo percentiles and summed ratios are count-weighted and Simpson-prone; (c) M1 clocks are calendar-elapsed and include human wait; (d) several "yes (M1)" claims are narrower than claimed (`rework_proxy_items` is a count only; per-mission k/N renders `0/0` until first completion; scope drift exists only inside done+estimated `schedule_variance` rows). What survives is a smaller set, restated with three invariant rules:

1. **Self-referenced, not pooled.** An indicator translates across repos when each row compares an item to its *own* human commitment (accepted range, declared scope, declared base), never to another repo's history. Cross-repo roll-up is a **count of items by state**, or a **table of per-repo rows**, never a pooled percentile or summed ratio.
2. **Progress is since-inception; pace is rolling.** Two names, never one number that switches meaning.
3. **Every row carries its measurability** (n, coverage ratio, censored/open count, clock label). A missing capture prints as em-dash or "unknown", never 0.

## 3. Drop (one-line refutation each)

- **Items delivered to date (standalone count)** — arithmetically absolute, semantically relative to observation length and task cut; changes no decision without N (→ completeness) or a rate (→ throughput). Sources: `report.mjs:128`, SPEC §6.9 line 184.
- **Pooled cross-repo velocity (median of summed weekly counts)** — count-weighted by the finest-cutting repo, starved by staggered onboarding, no coverage end; the spec refuses forecasts anyway. `metrics.mjs:22-29,106-108`.
- **Summed schedule-variance bands ("programme slip")** — signed hours cancel (A −30 h, B +30 h ⇒ 0) and concurrent missions double-count; programme slip is the campaign's own band.
- **Elapsed/active "flow-efficiency" ratio** — parallel dispatches make active > elapsed (unbounded, >100%); measures fan-out style, not waiting. Flow efficiency is out of scope by spec (§2 line 30).
- **Code churn (line-level; user item "churn rate")** — relative by construction (÷ lines added; language, generated files, squash regime, exclusion manifest); only relative churn predicts defects (Nagappan & Ball 2005); not in the 18-event model; perverse incentives. Per-repo engineering diagnostic outside the monitor at most.
- **Agent change acceptance / merge rate** — encodes close-and-reopen vs push-to-PR convention; at task level collapses to `1 − cancelled_share`; only 35.7% of agentic-PR rejections are genuine failure (`~/dev/dm-kb/SGHQ/programs/ai-transformation/asdlc-quality-lens-research.md:309`). Restate, if ever, as "cancelled with reason `rejected_output`, matured 30 d, per repo/class count".
- **Mission turnaround / hand-off gap (pooled P50/P85)** — pairs by plan `sequence` not chronology (`metrics.mjs:166-172` vs SPEC §5 line 79), drops overlapping pairs, calendar-dominated (fixture gap = one overnight, `metrics.test.mjs:55-56`); the open hand-off is structurally excluded. The DevEx citation does not mention handoffs. See §6 for the surviving "open hand-off age" form.
- **Change size / batch size distribution** — depends on exclusion manifest, branching topology (no per-task diff under mission squash) and the PM's own cut; no transferable threshold. Surviving form is a per-repo guardrail *flag* (`guardrail_breached` count) paired with `scope_declared`, not an indicator.
- **MdMRE / PRED(25) / MAE as headline** — research-grade accuracy statistics that add no PM decision beyond median work_ratio + hit_rate; MRE is asymmetric (Kitchenham et al. 2001; Foss et al. 2003); MAE scales with task size. Keep in the JSON envelope only.
- **Per-`accepted_by` estimate cut** — barred by SPEC D13 (line 48); the METR "explains" claim is an analogy, not a finding.
- **Aging WIP vs stratum P85 as a cross-repo number** — comparator is the repo's own history by definition (Kanban Guide SLE); the same 30 h item is "under" in one repo and "breached" in another. Per-repo only, M2, labelled relative.

## 4. Time window — the rule

**Rule: progress is since-inception; pace is rolling. Two named indicators, never one number that switches meaning.**

- **PROGRESS ("delivered to date")** = the `k` in mission/campaign completeness. Window = half-open `[plan observation_start, cutoff)` for that plan. It is since-inception by construction, always printed as `k/N` against endpoint scope (never k alone), includes partial-week completions, counts a reopened item once (first completion), and resets only on a new run. Cross-repo: the count-of-missions-by-state roll-up from §1, evaluated at **one shared `--cutoff`** after `backfill --git` in every repo. Proxy completions (`done_basis: proxy`) printed beside k, never inside it (M1 `status done=` currently includes them — `timeline.mjs:107`).
- **PACE (throughput and everything derived from it: cycle-time percentiles, fix rounds, corrective events)** = a **rolling window of whole UTC ISO weeks**, per repo. Reason: every source treats these as rates per unit time over a bounded window — DORA's instrument asks about the last six months and values metrics for "telling you if you are improving" (https://dora.dev/guides/dora-metrics-four-keys/); Four Keys computes medians over the last three months; Little's-law reasoning holds only over an interval where WIP is stable and arrivals ≈ departures, which a since-inception window over a changing harness (new model, new gates) never satisfies (https://www.leanability.com/en/blog/2017/08/littles-law-and-system-stability/, https://www.55degrees.se/blog/post/littles-law-assumptions); the dm-kb WPSE precedent showed one board reading 51/week over 3 weeks vs 27.5/week over the fully observed W33–W36 (`~/dev/dm-kb/tools/wpse-maturity/README.md:96-104`), so the window keys must print with every rate. A since-inception *rate* dilutes a current stall with old good weeks and its denominator differs per repo — not recommended.
- **Concrete parameters.** Weekly series zero-filled only within `[observation_start, plan close)` (add the coverage END to `weekKeys`, `metrics.mjs:22-29`); current partial week printed flagged, never in a median; per-repo velocity = median (not mean) of the last **K whole covered weeks** ending at the last completed Monday before cutoff, same K in every repo, three fixed K values: **4** (trend), **12** (headline; ≈ Four Keys' three months, above the n≥7 P85 floor), **26** (DORA's six-month stability horizon); below `profile.minWholeWeeks` (3) render em-dash, never 0; annotate or reset the baseline at a process change (model swap, gate change) rather than averaging across it.
- **Polyrepo.** Per-repo series only. No pooled velocity (§3). Where a cross-repo pace figure is demanded, roll up at the granularity-free level: missions/campaigns completed per window (a count of state transitions), over the common covered interval `[max(observation_start_i), min(close_i, cutoff))`. Percentile cohorts (cycle time) are fixed by **start** in window with the still-open count printed, so right-censoring is visible.

Answer to the user's "rolling vs since project start": **both, under different names** — `k/N since plan start` on the status page next to `closed per week, last 4/12 whole weeks` with n. Never an items/week averaged from day one.

## 5. Churn — what to adopt

Four things are called churn; adopt two, guard with one, reject one.

**Adopt (the user's "churn rate", answered as two rows):**

1. **Fix rounds per reviewed task** (pre-merge) — `tasks with ≥1 rework_observed ÷ completed tasks with ≥1 review-stage dispatch or review_requested`, per repo, per tier, two numerators (hook fix-dispatch, git address-review) deduped by `meta.round`; `unknown` when no review capture in the window. Read as a lower bound on M2 `first_pass_rate`. Decision: for a class/repo with an unchanged review policy, a rising value → human in the loop or smaller batches for that class; a review-policy change resets the baseline. Printed beside every per-repo throughput row as the mandatory stability pair (DORA 2024 reported throughput and stability both down with AI adoption; DORA 2025 throughput up with instability persisting — https://redmonk.com/rstephens/2025/12/18/dora2025/, https://dora.dev/research/2024/dora-report/2024-dora-accelerate-state-of-devops-report.pdf).
2. **Post-merge corrective events per exposed task** (post-merge) — as in §2: reopen-after-done, revert of the done sha, or `--fixes`-linked task within H = 14 days; denominator = tasks merged ≥ 14 days before cutoff; credited to the originating repo; per repo and class; pooled share only when every repo's exposure is complete and always beside the per-repo table. This is the harness's escaped-defect signal and the only churn form that attributes across repos.

**Guard:** scope-stability flag (§2) as the validity caveat on pace and estimate figures.

**Reject:** line-level code churn (relative, regime-dependent, outside the event model) and PR rejection/acceptance counts (64% non-failure noise). Do not read `cancelled` as churn until it carries a reason.

**What the harness must capture** (all small additions to `DM/hooks/dispatch-hook.mjs`, `DM/scripts/lib/timeline.mjs`, `DM/references/event-model.md`):
- Stage classification from `meta.stage` set by the orchestrator, not a vocabulary regex; a per-item `dispatches_by_stage` histogram (so "reviewed" is knowable).
- `meta.round` on fix dispatches and `address review N` commits, for dedupe across hook + git paths.
- `coverage.rework = {hook_fix, git_address_review}` per repo/window, so pooling is gated on rework capture, not start-source coverage.
- `cancelled --reason {rejected_output | descoped | superseded | duplicate | invalid}`; task `origin {human | agent}`.
- `--fixes <repo>/<item_id>` on fix tasks (repo-qualified id) and revert detection against the task's done sha set (`meta.git_sha`).
- Review events with an author-kind flag (human / agent-reviewer / bot) — M2.
- `blocked --reason {technical | scope | decision | dependency | review-wait | environment}` mirroring the PM agent's classify step (`/Users/Daniel_Sallai/dev/sdlc-skills/bundles/feature-development/agents/project-manager/AGENT.md:440-447`).
