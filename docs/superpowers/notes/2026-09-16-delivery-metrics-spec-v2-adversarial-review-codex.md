## Verdict

needs-changes

| F1 | major | observation-retraction-missing | §6.2; §6.5; §6.9 | **An erroneous completion cannot be withdrawn.** Corrections replace revisions within an observation whose identity includes item and event. There is no retraction/tombstone status or event. If a CLI observation mistakenly marks A done instead of B, correcting B creates another observation; A's completion survives. Recording a reopen is explicitly a real subsequent episode and preserves A's first throughput and duration. Correcting `at` cannot express “this never happened.” This also prevents repair of wrong-item adapter attribution without rewriting the ledger or inventing a lifecycle. | S:136–146 defines the closed vocabulary, identity and correction rules; S:211–212 exposes correction/batch commands; S:284–290 preserves first completion on reopen. The correction tests at S:439 cover changing a timestamp, not withdrawing a fact. | Define an immutable observation retraction with target identity/revision, reason, evidence and retry semantics. Specify whether it withdraws just that source or invalidates the logical occurrence, how lower-priority evidence is reconsidered, and how dependent transitions are quarantined/repaired. Test mistaken done, wrong-item attribution, retraction with a surviving git observation, and later reinstatement, including historical cutoff replay. |
| F2 | major | dedup-destroys-source-precedence | §3 D6; §6.2 | **Source ordering still does not select a unique observation in all admitted cases.** Two different CLI retry tokens may assert the same transition and basis at 11:00 and 12:00. They have different observation identities, so neither duplicate nor same-identity revision-conflict rules apply. Both rank `cli`; D6 has no rule to choose between them or reject their disagreement. The same issue can arise when local merge and mapped PR observations both use `git`. Sorting occurrences afterward is not a conflict policy: replaying both can either count an invalid second done or select a clock accidentally. V1's cross-source loss is fixed, but its deterministic selection requirement remains incomplete. | S:37,138–148; specifically S:144 limits identity conflict to one observation/revision, while S:146 groups multiple observations and applies only source priority. S:251–253 permits both local and PR completion evidence. | After revision collapse, define disagreement handling among equally ranked observations of one transition/basis. For example, coalesce equivalent clocks and quarantine unequal clocks unless an explicit supersession resolves them. Specify what is compared and whether lower-priority evidence remains usable. Test two CLI observations and local-git plus PR observations in both file/arrival orders, rather than relying on lexical id order. |
| F3 | major | plan-ledger-transaction-gap | §6.1; §12; §17 AC-11 | **Mid-append recovery has no byte-level contract.** The prescribed recovery appends missing observations, but a crash can leave an unterminated JSON prefix at EOF. Appending the missing full JSON line directly produces one malformed line containing both prefix and replacement; counting corruption does not recover that observation. Repair by truncation would be an exception to append-only storage, while repair by delimiter/quarantine needs explicit rules. Manifest publication must also verify replayable records, not merely the presence of expected bytes/hashes. “Crash before/mid append” is listed as a test without defining its expected on-disk repair. | S:103,114 specifies append-only files, fsynced append, manifest publication and append-missing recovery; S:146 says corruption is counted; S:441,513 promises crash recovery without lost created occurrences. | Specify durable intent contents and ordering, detection of the last complete record, and an explicit torn-tail repair policy that preserves all committed records. State whether uncommitted tails may be truncated or must be quarantined/delimited, and require record-level manifest verification before publication. Inject termination at byte offsets including partial UTF-8, partial JSON and missing newline; retry must recover exactly one parseable observation without damaging prior committed transactions. |
| F4 | major | shared-lock-excludes-existing-writers | §6.1; §6.12; §13 M-1 | **The compatibility amendment locks sync, but existing writers and export readers can still race it.** The universal “all writers, snapshot readers” requirement has no corresponding migration scope beyond tokenomics shared sync. `appendLine`, scope updates and gate appends currently write before/outside sync; batch-cost reads live files and scopes independently. A delivery sync holding the proposed lock therefore does not prevent a tokenomics append during git staging/merge, a scope rewrite during snapshot import, or a changed input between cost computation and provenance hashing. Upgrading only the named sync function cannot establish the promised shared critical section or coherent export manifest. | S:114–116,350,460–466. TOK/hooks/telemetry-capture.mjs:120–123,1403–1419 writes before calling sync; TOK/scripts/work-scope.mjs:46–48,74–90 rewrites scopes without a lock; TAW/scripts/gate/gate-case.mjs:202–221 appends independently; TOK/scripts/batch-cost.mjs:724–745 reads ledger/live/scopes then writes cost. | Enumerate every participating writer/reader and include their compatibility amendments, lock ordering and acquisition boundaries in M-1/M3; avoid wrapping a writer and then recursively acquiring its lock in sync. Alternatively specify a coherent immutable-snapshot/retry protocol for inputs outside the lock. Capability detection must cover the producers required for that guarantee, not just active sync. Add concurrent gate/scope/session-write versus sync/import/export fixtures proving that published hashes describe the bytes actually used and that no writer dirties an in-progress merge. |
| F5 | major | estimate-actual-boundary-undefined | §6.3–6.4; §6.10; §17 AC-10 | **Matching units does not identify the actual being estimated.** The accepted estimate schema says only `h = elapsed calendar hours`; it does not bind a start/finish metric. A task created Monday, dispatched Wednesday and merged two hours later has a roughly 50-hour lead time and a two-hour cycle time. Both are valid elapsed-hour columns in the spec, but comparison with the same accepted 1–3 h range produces opposite accuracy results. “Comparable actual” and “before measured start” consequently leave both the numerator and late-acceptance cutoff to implementation. Parent estimates also need an explicit boundary rather than an unspecified “declared ... boundary” absent from the example schema. | S:158–168,185–200; S:303–306 defines multiple elapsed-hour actuals; S:322–324 and S:512 require comparable accuracy/schedule comparisons without binding the estimate to one. R05:234,244 requires named actuals/denominators rather than interchangeable measures. | Bind each estimate to a versioned actual metric and start/finish basis, or prescribe one explicit mapping by level/unit and reject other meanings. Include that binding in the accepted digest and use its start for timely acceptance. State how missing starts, parent-derived timing and commit proxies affect eligibility. Test one item with different lead/cycle/commit durations and acceptance between creation and dispatch; expected ratio, hit rate and eligibility must be uniquely determined. |
| F6 | major | reopen-age-baseline-mismatch | §3 D7; §6.9–6.10 | **Reopened age is compared against a different lifecycle population.** `work_item_age` resets to latest reopen, while the P85 comparator and calibration contain only first-build-to-first-completion cycles. Reopen-to-now is a repair/second-episode clock; matching class and level does not make it comparable to original delivery cycles. A task taking ten days to first completion, reopened an hour ago, displays one hour against the original-cycle P85; further close/reopen cycles reset that warning again. First-completion conservation is legitimate, but does not justify this SLE comparison. | S:38,290,303,309,324,327. [Kanban Guide 2025, Definition of Workflow and Flow Metrics](https://kanbanguides.org/the-kanban-guide/) ties age, cycle time and SLE to the workflow's defined start/finish boundaries. The mismatch here is the spec's distinct episode boundaries, not a claim that Kanban forbids reopening. | Keep first-open age versus first-cycle P85 for never-completed items. Label reopened age separately and compare it only with a sufficient, separately collected reopen-to-recompletion distribution; otherwise omit its P85 warning as not comparable. Preserve total/history age visibly if needed. Test first episode, long original cycle plus recent reopen, and repeated reopen episodes without silently reusing the first-cycle reference population. |

## Not found / explicitly fine

- Cross-source observations now survive append/dedup and earlier CLI clock corrections can outrank git; F2 concerns the remaining equal-priority case.
- Scope/gate/receipt proxies are explicitly separated from observed cycles, observed throughput and calibration; cluster dispatch no longer fabricates individual case starts.
- Both gate-log locations, required-N proof, tested/base revision provenance and separate landing are required. The new gate binding is honestly declared provenance, not falsely attributed to the current logger.
- Stable run/item identities, migration mappings, tombstones and generation-bound joins address the v1 reused-id/card-log identity failures.
- Missing/partial reviews no longer become first-pass success; review eligibility has explicit denominators, and fix activity remains a rework proxy.
- Copilot automatic capture and live pending starts are genuinely parked. Claude child-path/worktree behavior remains an explicit M2 spike prerequisite, consistent with the documented [SubagentStop fields](https://code.claude.com/docs/en/hooks#subagentstop).
- Full-message Workflow resolution, plan/session binding and participating-roster admission replace the v1 first-line and plan-exists assumptions; P-1 names the required standards amendment.
- Owned inner ignores and semantic removal address the v1 transient-staging and byte-restoration problems; real staging checks are required.
- UTC half-open windows, carried-in history, first-completion cohorts, whole-week conservation and common observation coverage are now explicit. Fixed temp-git backfill and mapped PRs avoid moving-branch totals and squash/title dependence.
- Accepted estimate provenance, descriptive confidence bands, explicit midpoint/MRE formulas, unknown probability and genuine sub-minute durations are handled explicitly; F5 concerns the remaining actual-boundary selection.
- Batch/case export-only cost consumption avoids raw live/final double counting; direct/loaded allocation, tokens-only, PROVISIONAL, DRIFT and snapshot freshness have explicit treatments. F4 concerns coherent capture of those inputs, not a request to restore raw cost recomputation.
- DORA is correctly excluded without deployment evidence; these flow clocks do not claim to implement [DORA's delivery metrics](https://dora.dev/guides/dora-metrics/).
- Forecasting and Little's Law are genuinely parked. No per-person leaderboard or fabricated baseline is specified; speed/volume strata require quality or explicit unknowns.
- The Kanban Guide does not mandate a universal sample floor or specifically P85. V2 states its empirical percentile floors; no unsupported “P85 must have 20 samples” requirement is imposed here.
- Orphan registration, factory attachments, on-demand roles, installed tests, strict frontmatter, stdlib ESM and marketplace regeneration match repository patterns. No obsolete host-mode architecture is introduced.
- No implementation tests were run: delivery scripts do not exist yet. Review changed only this note; repository and standards inspection was read-only.
