# OST method — the disguise test, the Olsen score, and the derived-file format

The three deterministic pieces of `opportunity-tree`. Adapted from phuryn/pm-skills (MIT,
© Pawel Huryn) for the Olsen score and OST framing, and shinpr/claude-code-discover (MIT) for the
3+-solutions phrasing of the disguise test. The overlay-persistence design is house-authored.

## 1. The disguise test (the 3+-solutions gate)

Before a Problem is classified `node_type: opportunity`, it must clear one test. Torres states the
underlying idea qualitatively — an opportunity that admits only one possible solution *is* that
solution, wearing an opportunity's clothing:

> **Is there more than one way to address this?**

This bundle applies a deliberately stricter working threshold:

> **If an opportunity cannot generate 3+ different solutions, it may be a solution in disguise.**

Three, rather than Torres's two, is the phrasing from shinpr/claude-code-discover; it catches
near-misses a two-solution test lets through. Treat a node that yields exactly two as borderline —
worth the PO's attention, not an automatic masquerade. (Torres separately recommends comparing at
least three *solutions* once an opportunity is already valid. That is a decision-quality practice
about choosing between options, not a test of the opportunity — don't conflate the two.)

Apply it concretely — try to name three *genuinely different* ways to address the need:

- **Clears the gate** — the node states a customer *need* broad enough that three distinct
  approaches plausibly serve it. Example need: "new users cannot tell which data sources they
  have already connected" → a checklist, a connection-status badge, an onboarding summary screen…
  three different solutions. It is a real opportunity.
- **Fails the gate** — the node names one specific implementation. Example: "add a CSV export
  button." There is essentially one way to do that — it *is* the solution. Flag it
  **solution-masquerade**, name the opportunity it might serve ("users need to get the summary
  into their own tools" — which *does* spawn 3+ solutions), and hand the call to the PO.

The gate is a **flag, not a veto**. The skill surfaces the masquerade and the candidate
opportunity behind it; the PO decides. The skill never silently writes `node_type: opportunity`
onto a node that failed the test.

## 2. The Olsen Opportunity Score

Per opportunity, from evidence (interviews, surveys) — never invented:

- `x_importance:` — how much the need matters to the customer, 0–10.
- `x_satisfaction:` — how well it is served today, 0–10.
- `x_olsen_score:` = **`importance × (1 − satisfaction/10)`**, rounded to one decimal.

The score is highest when a need matters a lot (high importance) and is served badly (low
satisfaction) — the underserved needs worth building for. Worked examples:

| importance | satisfaction | score |
|---|---|---|
| 9 | 2 | 7.2 |
| 8 | 5 | 4.0 |
| 6 | 9 | 0.6 |

**Missing data ⇒ `n/a`.** If either `x_importance:` or `x_satisfaction:` is absent, the score is
`n/a` (not zero, not a guess) — an opportunity with no evidence yet still appears in the tree, it
just is not scored. `prioritize-bets` reads `x_olsen_score:` as one input; `n/a` means "gather
evidence first."

## 3. The derived-file format — `docs/discovery/outcome-tree.md`

Regenerated in full every run — a plain markdown board, no query-plugin dependency and no vault
tool required to read it. **Determinism is the contract**: identical source frontmatter must produce a
byte-identical file, so the format below carries **no timestamp and no run-specific text in the
body**. Ordering is fixed:

- Sections: one per **ratified** (`status: active`) outcome row, in the order the rows appear in
  `docs/discovery/outcomes.md`'s table.
- Opportunities within a section: by `x_olsen_score:` descending, `n/a` last; ties broken by slug
  ascending.
- Solutions within an opportunity: by `id` ascending.
- Assumption-tests within a solution: by path ascending.
- Orphans: a single trailing section, entries by path ascending.

Exact skeleton (links are relative to the repo root):

```markdown
---
type: outcome-tree
title: Outcome-solution tree
status: active
x_derived: true
---

<!-- GENERATED by opportunity-tree from the node_type:/parent: overlay.
     Do NOT hand-edit — re-run the skill; hand edits are reverted on the next regeneration. -->

# Outcome-solution tree

Rendered from the `node_type:` / `parent:` overlay on existing Discovery artifacts. One tree per
ratified outcome row; orphans (a `parent:` that resolves to no node here) are listed last.

## <outcome row's `outcome` sentence> — `docs/discovery/outcomes.md#<id>`

- **Opportunity** · Olsen <score|n/a> — [<problem title>](docs/discovery/problems/<PRB-NNN-slug>.md)
  - **Solution** `<status>` — [<hypothesis title>](docs/discovery/hypotheses/<HYP-NNN-slug>.md)
    - **Assumption test** — [<title>](docs/discovery/evidence/<kind>/<...>.md)

## Orphans (parent resolves to no node in the tree)

- [<title>](docs/discovery/<...>.md) — `parent:` → `<unresolved value>`
```

If an outcome has no opportunities yet, render the `##` section with a single
`- _(no opportunities mapped yet)_` line — still deterministic. If there are no orphans, render
the Orphans heading with `- _(none)_`. Never omit a heading conditionally on run-specific state
that could differ between two regenerations.
