# Rules — test-author

1. **Never ask for info already in `.agents/manual-qa/app_profile.md`.** Read the profile before the first user interaction; never prompt for base_url, credentials, or anything documented there.
2. **Never hardcode a domain.** All URLs in test cases use `{{base_url}}` — the literal placeholder, never an actual hostname.
3. **One behavior per test case.** Each TC must test exactly one thing. If the user's sketch spans multiple behaviors, split it into multiple files.
4. **Every expected result must be snapshot-verifiable.** Acceptable forms: URL change, visible text, element present/absent, field value. "Page works" or "it succeeds" is not acceptable.
5. **Teardown required if the test mutates persistent state.** Any TC that creates data, logs in, or modifies stored state must include a Teardown section.
6. **Ask all gaps in one message.** Never send multiple rounds of questions for a single test — group everything into one message and wait.
7. **Show the file after writing.** Always output the full file content after saving, so the user can review without opening the file.
8. **When the input is a specification (acceptance criteria, a user story's AC bullets, or any other explicit contract — not a rough idea, not a bug report, not an already-observed behavior), the specification wins.** Write the test to match exactly the scenario and data the input states, even if `app_profile.md` or a sibling TC documents a live fact that contradicts it — that contradiction is exactly what running the test is supposed to catch, not something to resolve by rewriting the test. Do not: substitute different test data/credentials/subjects than what the input explicitly names to make the criteria pass, invert an expected result to match observed reality instead of the stated criterion, or split off a second "what actually happens" file the input never asked for. If you're aware of a documented fact that may contradict a specified criterion, add ONE line noting it (e.g. in `## Notes`: "Per app_profile.md, current behavior may not satisfy this criterion — verify at run time") — a note, never a rewrite of the test itself. This rule does NOT apply when the input already discloses the known issue itself (a bug report, or a criterion that explicitly names a known/tracked defect) — in that case, keep documenting the disclosed behavior as the expected outcome, same convention as always.
